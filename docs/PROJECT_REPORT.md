INTRODUCTION
1.1 Background to the Study
The rapid growth of artificial intelligence has fundamentally altered how software is developed. Large language models (LLMs) such as Meta's Llama, Google Gemini, and OpenAI GPT-4o can now produce complete PHP controller methods, Eloquent model relationships, and REST API endpoint logic within seconds. Studies consistently report that a growing majority of professional developers now use AI coding assistants in their daily workflow, and the productivity gains are substantial for routine tasks such as boilerplate generation, documentation writing, and algorithm scaffolding (Bajaj et al., 2024).
Despite these advances, a significant and persistent gap remains between AI-generated code and production-ready software. Modern web frameworks such as Laravel — PHP's dominant MVC framework, handling over 60 million monthly Composer package installations — impose strict architectural conventions: PSR-4 namespace resolution, service container bindings, Eloquent ORM relationship declarations, REST resource routing, and environment-specific configuration management. When an AI model generates a Laravel REST API controller without access to the live application's database schema, directory structure, and registered service providers, the result frequently fails at runtime even though it passes static syntax analysis. The error manifests not as a language-level mistake, but as a framework-level architectural violation — a class not found because its namespace does not match the directory, a model method call that does not correspond to any column in the actual database, or a service that was never registered in the container (Xia et al., 2023).
This runtime validation gap — the inability of AI tools to confirm that generated code actually executes correctly in a real Laravel environment — is the central problem this project addresses. The platform developed in this study, referred to throughout as the AI-Enhanced Code Repair Platform, closes this gap by combining four components: an isolated Docker execution sandbox pre-loaded with PHP 8.3, Laravel 12.x, Pest 3, and Laravel Boost; a FastAPI coordinator implementing an iterative agentic repair loop; a multi-provider LLM routing layer; and a real-time web interface that streams repair progress to the developer. Together these components enable a workflow in which submitted Laravel code that fails at runtime is automatically diagnosed, corrected, re-executed, and mutation-tested until a verified, production-ready version is produced.
The platform was designed and built in the period between September 2025 and May 2026, incorporating the Laravel AI ecosystem packages released during that window — specifically Laravel Boost (released August 2025), which exposes over 15 MCP tools for AI agents, and the Laravel AI SDK (released February 2026). This timing positions the project at the frontier of the Laravel AI ecosystem and ensures that the repair methodology accounts for the latest framework conventions and tooling standards.
1.2 Problem Statement
Despite the capabilities of modern LLMs, autonomous code repair systems applied to complex PHP/Laravel REST APIs fail for four distinct reasons, as identified through a review of the automated program repair (APR) literature and confirmed by the preliminary experiments that motivated this project.
First, there is a lack of deterministic verification. AI-generated code is evaluated at prompt time, not execution time. Without running the code in a real PHP interpreter with a real Laravel application context, there is no way to confirm that the output is correct. Static analysis tools such as PHPStan and Psalm can catch type errors and undefined variables, but they cannot simulate database queries, service container resolutions, or middleware stack execution.
Second, LLMs suffer from contextual hallucinations when generating framework-specific code. Without access to the application's actual database schema, namespace directory layout, and registered service providers, models routinely generate plausible-looking but architecturally incorrect code — for example, referencing a model class that does not exist, or calling a method on a facade that has not been bound in the container.
Third, automated repair loops can become stuck in cycles in which the same incorrect fix is applied repeatedly. Without a mechanism to detect stagnation and force a different diagnostic strategy, a five-iteration repair loop can exhaust its budget applying the same inadequate patch to the same persistent error.
Fourth, existing repair tools provide poor observability. When an automated tool silently modifies code and returns a result, the developer has no insight into what changed, why it changed, or whether the generated Pest test that accompanied the repair actually exercises the critical logic paths. This opacity undermines developer trust in the repair output and limits the tool's practical adoption.
1.3 Aim and Objectives
The aim of this project is to design and implement an AI-powered iterative code repair platform for PHP/Laravel REST API applications that validates and autonomously corrects AI-generated backend code through Docker sandbox execution, Laravel Boost context enrichment, and mutation-tested quality verification.
The specific objectives are as follows:
1.To review existing literature on automated program repair (APR), Docker sandboxing, large language model code generation, and the Laravel AI ecosystem, identifying the research gap that this project fills.
2.To design a secure, isolated Docker sandbox environment pre-loaded with PHP 8.3, Laravel 12.x, Pest 3, and Laravel Boost, suitable for executing untrusted AI-generated code without risk to the host system.
3.To implement a FastAPI coordination service that manages the iterative agentic repair loop, including multi-provider LLM routing, Server-Sent Events streaming, and SQLite-based forensic logging.
4.To integrate Laravel Boost as an MCP context provider, supplying the repair prompts with live database schema information and relevant framework documentation to reduce AI hallucination.
5.To evaluate the platform's repair effectiveness through a structured batch evaluation, including ablation studies that measure the independent contribution of Boost context enrichment and the Pest mutation testing gate.
1.4 Significance of the Study
This study makes several contributions to the fields of automated program repair and AI-assisted software development.
For the software engineering research community, the platform introduces a novel evaluation methodology for PHP/Laravel APR systems that incorporates mutation testing as a second-order quality gate. Mutation testing — deliberately injecting faults into repaired code to verify that the generated Pest tests catch them — produces a more rigorous quality signal than functional test passage alone, and the use of this methodology in the context of AI-driven repair has not been previously documented in the literature.
For practitioners, the platform offers a practical tool that can be integrated into existing development workflows either through the web interface or through the MCP server integration, which allows developers using Cursor and Claude Code to invoke the repair engine without leaving their editor. This deployment model positions the platform as a natural complement to the official Laravel AI ecosystem.
For the Laravel community specifically, this project documents the integration of Laravel Boost's MCP context tools into an autonomous repair system — the first published study to do so following Boost's release in August 2025. The ablation results quantify the improvement that Boost context enrichment provides over context-free repair, establishing a baseline for future research into framework-aware LLM prompting.
1.5 Scope of the Study
This study focuses on the design, implementation, and evaluation of a code repair platform for PHP/Laravel REST API applications. The platform targets three categories of runtime errors most frequently produced by AI code generation in the Laravel context: missing model or class references, incorrect namespace declarations, and missing import statements. These categories were selected based on a preliminary survey of the APR literature and are representative of the framework-level architectural violations that static analysis tools cannot detect.
The platform is evaluated using Meta Llama 3.3 70B (served via Groq and NVIDIA NIM inference endpoints) as the primary LLM provider, with additional providers (Gemini, Cerebras, and local Ollama) available through the multi-provider routing layer. The evaluation uses a maximum of seven repair iterations per case and a Pest mutation score threshold of 80 percent. Results are compared against ablation variants with Boost context disabled and with the mutation gate disabled.
The study does not address repair of non-Laravel PHP applications, front-end JavaScript, or Python code, although the modular architecture permits extension to these domains. It also does not evaluate the platform in a production environment with real user submissions; all evaluation is conducted using a curated batch manifest of representative test cases.
1.6 Definition of Terms
Automated Program Repair (APR): The use of automated techniques — including heuristic search, genetic algorithms, symbolic execution, and large language models — to detect and correct software defects without human intervention.
Laravel: A PHP web application framework following the Model-View-Controller (MVC) architectural pattern, providing a structured development environment for building REST APIs and full-stack web applications.
Docker: An open-source containerisation platform that packages applications and their dependencies into isolated, reproducible runtime environments called containers.
Large Language Model (LLM): A deep learning model trained on large corpora of text, capable of generating and understanding natural language and programming code.
Model Context Protocol (MCP): An open standard enabling AI models to securely access external tools and data sources through a standardised JSON-RPC 2.0 interface.
Laravel Boost: An official Laravel Composer package released in August 2025 that functions as an MCP server, exposing real-time database schema, application logs, and framework documentation to AI coding agents.
Pest: A PHP testing framework with a clean syntax for writing unit, integration, and feature tests. Version 3 includes a mutation testing plugin (pest --mutate) that verifies test suite robustness.
Mutation Testing: A quality assurance technique in which deliberate faults (mutations) are introduced into source code, and the test suite is evaluated for its ability to detect those faults. A high mutation score indicates a thorough test suite.
Server-Sent Events (SSE): A server push technology enabling a server to stream real-time updates to a browser client over a single HTTP connection.

2.2 Automated Program Repair
Automated Program Repair (APR) refers to the use of computational techniques to automatically fix bugs in software without requiring direct human intervention. The field has evolved considerably over the past decade, moving from simple template-based fixes to sophisticated machine learning approaches that can understand code semantics and generate contextually appropriate patches. Zhang et al. (2024) provide a comprehensive survey of the integration of LLMs into software engineering, documenting this evolution across multiple research communities. This section traces three generations of APR techniques, identifying the strengths and limitations that motivated the approach taken in this project.
The first generation of APR relied on search-based techniques. Early systems used genetic programming to evolve program variants by applying mutation and crossover operators to the abstract syntax tree of buggy programs, accepting patches that caused all tests to pass. These approaches demonstrated that automated repair was feasible on real-world programs but suffered from a fundamental limitation: they frequently produced patches that caused the failing test to pass without genuinely fixing the underlying defect — a problem known as overfitting (Huang et al., 2025). The patch appeared correct but was semantically incorrect, masking the bug rather than resolving it.
The second generation introduced constraint-based and semantics-based repair. Ye, Martinez, Luo, Zhang, and Monperrus (2022) demonstrated through SelfAPR that self-supervised learning on project-specific code, combined with test execution diagnostics, could produce higher-quality patches than earlier generic approaches. Their system generated training samples by perturbing correct versions of the same project, capturing project-specific conventions and logic patterns. This approach produced more reliable patches but required significant computational resources and did not address framework-level architectural violations.
The third generation, enabled by deep learning, treated bug repair as a sequence-to-sequence translation task. Lutellier et al. (2020) introduced CoCoNuT, which combined multiple context-aware neural translation models in an ensemble to generate repair patches. The key insight was that incorporating the surrounding code context — not just the buggy line — substantially improved patch quality. However, even these models were limited by their inability to understand the broader architectural context of a framework-based application.
The emergence of large language models produced a paradigmatic shift in APR. Xia, Wei, and Zhang (2023) documented how LLMs — trained on billions of lines of code — could leverage their broad semantic understanding to reason about bugs in ways that earlier models could not, without requiring task-specific fine-tuning. Their work at ICSE 2023 demonstrated that directly prompting pre-trained language models could outperform specialised APR tools on standard benchmarks.
Building on this foundation, Bouzenia, Devanbu, and Pradel (2025) developed RepairAgent, the first autonomous LLM-based agent for program repair. RepairAgent was equipped with fourteen specialised tools for reading code, searching the codebase, applying patches, and running tests. This agentic approach — treating the LLM as an autonomous agent capable of planning its own debugging strategy using reasoning and acting cycles (Yao et al., 2023) — directly influenced the multi-role agentic architecture used in this project. RepairAgent successfully repaired 164 bugs on the Defects4J benchmark, including 39 bugs that no prior technique had addressed.
Jiang, Liu, Lutellier, and Tan (2023) further showed that fine-tuning code language models on APR-specific data yielded 31 to 1,267 percent improvements in repair performance, underscoring how domain-specific adaptation dramatically improves patch quality. This finding is particularly relevant to the PHP/Laravel context, where the model's general training data may not adequately represent the framework's architectural conventions.
However, as Huang et al. (2025) observe in their comprehensive review of APR advancements, existing LLM-based APR systems share a critical limitation: they operate primarily on Python and Java codebases, and they assume that the patch verification environment closely matches the LLM's training distribution. PHP/Laravel applications violate this assumption in significant ways. The framework's reliance on runtime service container resolution, dynamic Eloquent model generation, and environment-specific configuration means that even syntactically correct, semantically coherent patches frequently fail at execution time due to framework-level violations that neither the LLM nor static analysis tools can predict without a live execution environment. This is the central limitation that motivated the design of the Docker sandbox and iterative repair loop in this project.
2.3 LLMs for Code Repair and Context Enrichment
The quality of LLM-generated code repairs is strongly correlated with the quality of the context provided to the model. Bajaj et al. (2024) provide a comprehensive survey of AI-driven advancements in automated program repair and code generation, identifying context availability as one of the three primary factors determining repair success alongside model capacity and evaluation methodology. The foundational work on code-trained LLMs by Chen et al. (2021), which introduced the Codex model and the HumanEval benchmark, established that language models fine-tuned on code can solve a substantial fraction of programming problems — but also highlighted that performance degrades significantly on tasks requiring project-specific context that was not present in the training data.
Jiang et al. (2023) demonstrated that fine-tuning code language models specifically for APR tasks using curated datasets substantially improves repair quality, with the improvement being most pronounced for framework-specific bugs where the model's general training data is insufficient. Their study evaluated ten different code language models across four APR benchmarks, establishing that the best-performing model could fix 72 percent more bugs than state-of-the-art deep-learning-based APR techniques even without fine-tuning.
A complementary approach to fine-tuning is retrieval-augmented generation (RAG), in which relevant contextual information — such as API documentation, database schemas, or similar past repairs — is retrieved and injected into the prompt at inference time. Liventsev, Grishina, Härmä, and Moonen (2023) demonstrated this principle through their Synthesize-Execute-Debug (SED) framework, which equipped an LLM with the ability to generate code, execute it, and iteratively debug failures using contextual information gathered from the execution environment. This approach — generating, executing, and refining based on runtime feedback — is architecturally analogous to the iterative repair loop developed in this project, though the SED framework operated on general programming tasks rather than framework-specific PHP code.
The release of Laravel Boost in August 2025 formalised the context-enrichment approach within the Laravel ecosystem. Announced by Taylor Otwell at Laracon US, Boost is an official Composer development dependency that runs a local MCP server within the developer's project (Otwell, 2025a). The server exposes tools including a database schema reader that returns live schema information for any table, an application log parser, and a documentation search endpoint covering versioned Laravel documentation entries. When a Laravel AI agent queries Boost before generating a fix, it receives the same quality of context that an experienced developer would consult when debugging — the actual table columns, the actual registered bindings, the actual directory layout — rather than relying on training-data approximations.
This project incorporates Boost as a component of the repair pipeline, integrating its context enrichment capabilities into the AI prompt construction process. The boost_service module queries Boost's schema and documentation tools before each AI repair call, structuring the retrieved context into the system prompt. The evaluation in Chapter Four examines the impact of Boost context on repair quality through an ablation study that disables Boost enrichment and compares the results against the full system.
2.4 Containerisation and Execution Security
Executing AI-generated code poses significant security risks. Pearce, Ahmad, Tan, Dolan-Gavitt, and Karri (2022) demonstrated in their IEEE S&P study that GitHub Copilot generates vulnerable code in approximately 40 percent of security-relevant scenarios, underscoring that AI-generated code cannot be trusted without independent verification. Docker containerisation has emerged as the primary mitigation strategy, providing process isolation, network restriction, and resource limits within a lightweight virtualisation layer.
Wong, Chekole, Ochoa, and Zhou (2023) provide a comprehensive analysis of container security in their Computers & Security survey, categorising threats using the STRIDE framework and identifying attack vectors across eleven categories. Their analysis of container isolation mechanisms — Linux namespaces, Control Groups (cgroups), and seccomp filters — directly informs the security configuration used in this project: network isolation (--network=none), memory limits (--memory=512m), process count limits (--pids-limit=64), and privilege escalation prevention (--security-opt=no-new-privileges:true).
Bhardwaj and Kumar (2025) present a lightweight Docker-based sandbox specifically designed for executing untrusted code, demonstrating that Alpine Linux base images combined with strict resource constraints can provide sufficient isolation without significant performance overhead. Their design principles — minimal base images, no network access, strict memory limits, and automatic cleanup — align with the sandbox architecture developed in this project.
For PHP/Laravel specifically, the execution environment must include not only the PHP interpreter but the full Laravel application scaffolding — routes, service providers, Eloquent model auto-discovery, and the Composer autoloader — to accurately reproduce the conditions under which the submitted code would execute in production. This requirement shaped the Docker image design described in Chapter Three, resulting in a multi-layer image that balances security constraints with framework completeness.
2.5 Mutation Testing as a Quality Gate
A critical challenge in automated program repair is determining whether a generated patch truly fixes the bug or merely causes the test suite to pass without addressing the root cause. This is the overfitting problem identified across the APR literature (Huang et al., 2025), and it remains a concern even with modern LLM-based approaches. Schäfer, Nadi, Eghbali, and Tip (2024) demonstrated in their IEEE TSE study that LLM-generated test suites often lack the thoroughness needed to serve as reliable oracles for patch validation.
Mutation testing offers a principled solution to this problem. Papadakis, Kintis, Zhang, Jia, Le Traon, and Harman (2021) provide insights from a large-scale study of mutation testing adoption among open-source developers, demonstrating that mutation scores provide a more meaningful measure of test suite quality than statement or branch coverage. The core principle is straightforward: deliberate faults (mutants) are introduced into the source code, and the test suite is evaluated for its ability to detect those faults. A high mutation score — the percentage of mutants killed by the test suite — indicates that the test suite thoroughly exercises the code's logical paths.
In the context of automated program repair, mutation testing serves as a second-order quality gate. A repair that passes functional tests but has a low mutation score is suspect: it may have been patched in a way that satisfies the existing tests without being genuinely correct. By requiring a minimum mutation score of 80 percent, this project's platform enforces a higher standard of repair quality than functional test passage alone. This threshold was selected based on the observation that mutation scores below 80 percent frequently correlate with test suites that do not exercise edge cases, boundary conditions, or alternative code paths — precisely the conditions that would allow fragile patches to pass into the codebase.
The Pest PHP testing framework includes a built-in mutation testing plugin (pest --mutate) in version 3, which performs AST-level mutations on the repaired source file and re-runs the test suite for each mutant. This integration is one of the reasons Pest was selected as the testing framework for the sandbox environment: it provides mutation testing capability without requiring an external tool such as Infection PHP.

3.2 Development Methodology
The platform was developed using an iterative prototyping methodology. This approach was selected because the project involved integrating multiple nascent technologies — Laravel Boost (released August 2025), Pest 3 mutation testing, and multi-provider LLM orchestration — whose interactions were not fully predictable at design time. A traditional waterfall methodology would have required complete specification of all component interfaces before implementation began, which was infeasible given the rapid evolution of the underlying AI ecosystem.
The development process proceeded in four major iterations over the period from September 2025 to May 2026. The first iteration established the minimal viable pipeline: a single Docker container running a Laravel 12 project, a single LLM provider (Groq), a basic repair loop that submitted code and returned the AI's response, and a minimal web interface for code submission. This iteration validated that the core concept — automated detection, LLM-based repair, and in-container execution — was architecturally feasible.
The second iteration added the multi-provider routing layer, the Boost context integration, and the Pest functional test gate. This iteration introduced the most complex integration challenge: querying Boost inside the container while the repair loop ran on the host, requiring careful orchestration of Docker exec commands and JSON response parsing.
The third iteration introduced mutation testing via Pest's --mutate flag, the escalation service for detecting stuck loops, the RAG-lite context memory for few-shot learning from past repairs, and the structured multi-role AI prompting (Planner → Executor → Reviewer). The fourth and final iteration focused on the web interface redesign, the prototype MCP server, and the batch evaluation framework for systematic performance measurement.
At the end of each iteration, all existing test cases from the batch manifest were re-run to verify that new features did not regress previously working functionality. This continuous validation ensured that the platform remained stable and evaluable throughout development.
3.3 Technology Stack
The backend coordination service is implemented in Python 3.12 using the FastAPI framework. FastAPI was selected for its native support for asynchronous programming through Python's asyncio library, its automatic OpenAPI documentation generation, and its tight integration with Pydantic v2 for request and response validation. The asynchronous design is essential for the repair platform because long-running Docker container operations and LLM API calls must not block concurrent user requests.
The Docker execution environment is built on the php:8.3-cli-alpine base image, layering Alpine system packages, PHP extensions (Redis and pcov for coverage collection), a full Laravel 12.x project, Pest 3 with the Laravel plugin and the mutate plugin, and Laravel Boost as a development dependency. The complete image build takes approximately five minutes on first run due to PECL extension compilation; subsequent builds use Docker's layer cache and complete in seconds.
The AI service layer implements a multi-provider dispatch architecture. All providers — Groq, NVIDIA NIM, Cerebras, Gemini, and DeepSeek — are accessed via OpenAI-compatible chat completion endpoints, meaning the single openai Python SDK handles communication across all providers with only a base URL change. Ollama is accessed through its local OpenAI-compatible REST endpoint for fully offline operation. The primary model used throughout development and evaluation is Meta Llama 3.3 70B Versatile, served through Groq's inference API for the planner role and NVIDIA NIM for the executor role. The active provider is selected at startup from the DEFAULT_AI_PROVIDER environment variable and routed through a dispatch dictionary in ai_service.py. Temperature is fixed at 0.0 for all providers to ensure deterministic, reproducible output.
SQLite handles all data persistence for the platform via the aiosqlite driver and SQLAlchemy 2.0 ORM. SQLite was selected for its zero-configuration deployment, ACID compliance, and suitability for the read-heavy, moderate-write workload generated by the repair evaluation. The database stores forensic records of every repair attempt, including the Boost context injected, the AI prompt sent, the model used, the patch applied, and the mutation score achieved — enabling post-hoc analysis of repair strategies. For cloud deployment, the platform also supports PostgreSQL via asyncpg, though the local development and evaluation environment uses SQLite exclusively.
The frontend is implemented using React with the CodeMirror editor library for PHP syntax highlighting and real-time rendering of applied patches. The browser connects to the SSE stream using the native EventSource API, receiving typed events (iteration_start, boost_queried, ai_thinking, patch_applied, pest_result, mutation_result, complete) that update the three-panel interface in real time.

3.5 The Iterative Repair Loop
The core of the platform is a thirteen-step orchestration loop, illustrated in Figure 3.2. Each iteration begins with PHP lint validation (php -l) to fast-fail on syntax errors before container provisioning. The code is then reflected upon to detect the PHP namespace and class name declared, enabling correct PSR-4 placement within the Laravel directory tree and composer dump-autoload registration. The code is then executed via php artisan tinker, capturing any runtime errors and stack traces.

If execution fails, the loop queries Laravel Boost for schema and documentation context relevant to the error type (step 6), retrieves similar past repairs from the RAG memory using a retrieval score computed as the weighted sum of error signature similarity and repair efficiency (step 7), and then performs a post-mortem analysis to diagnose the root cause of the failure (step 8). The planner agent designs a targeted fix strategy (step 9), and the executor agent applies the patch via patch_service (step 10).
After patching, the functional gate (step 11) executes the Pest test suite generated alongside the patch to verify baseline API behaviour. If the functional gate passes, the mutation gate (step 12) runs pest --mutate, requiring a mutation score of at least 80 percent before accepting the repair. Repaired code that passes both gates is stored in the database and returned to the developer via SSE (step 13). The 80 percent mutation threshold is deliberately stringent, as discussed further in Section 4.5.
3.6 Escalation Service
A critical component of the platform is the escalation service, which prevents the repair loop from getting stuck in cycles. The escalation service is triggered after every failed iteration and evaluates four independent conditions. If the last two AI diagnoses overlap by 70 percent or more, the service forces a completely different reasoning strategy. If patches fail repeatedly, it bans partial patch actions and demands a full file replacement. If the AI creates a dependency file but does not fix the original file, the service redirects the next iteration to focus on the original code. If the AI attempts to create the same missing file in consecutive iterations, the service blocks that action to prevent an infinite loop.
The escalation logic transforms the repair loop from a fixed strategy into an adaptive one, capable of recovering from the class of LLM reasoning failures identified in problem statement point three.
3.7 Laravel Boost Integration
Laravel Boost, released by Taylor Otwell in August 2025, provides the platform's context enrichment capability. This context is structured and injected into the LLM system prompt, giving the model the same situational awareness that a senior Laravel developer would draw upon when debugging.

3.8 Security Design
Every Docker container is provisioned with the following security constraints applied at runtime: --network=none to remove all external network access, --memory=512m to prevent memory exhaustion, --pids-limit=64 to block fork bomb payloads, and --security-opt=no-new-privileges:true to prevent privilege escalation. User code is injected via an in-memory tar archive constructed using Python's tarfile module; no temporary files are created on the host filesystem. Every container is unconditionally destroyed inside a Python finally block in repair_service.py, eliminating container resource leaks. The patch_service actively blocks AI patches that attempt to overwrite critical framework files (routes/api.php, .env, composer.json, pest.php). API keys are loaded exclusively via pydantic-settings from an untracked .env file.

4.8 Discussion
The evaluation results, while still pending final data population, reveal several insights from the development and preliminary testing of the platform that warrant discussion.
First, the iterative repair loop consistently demonstrated that runtime execution feedback is essential for PHP/Laravel code repair. During development testing, cases that failed due to framework-level violations — such as a missing use statement for the Illuminate\Support\Str helper, or a model referencing a non-existent database column — were undetectable by static analysis alone. The Docker sandbox caught these failures on first execution, enabling the AI to receive precise error messages and stack traces that guided targeted, effective patches.
Second, the multi-role agentic prompting architecture (Planner → Executor → Reviewer) proved more reliable than single-shot prompting. In preliminary testing, cases where a single prompt was sent to the LLM often produced patches that addressed surface symptoms without identifying the root cause. The Planner's diagnostic classification forced the system to commit to a specific repair strategy before generating code, reducing the incidence of aimless or contradictory patches.
Third, the escalation service provided a critical safety net. Without escalation logic, the repair loop could become stuck repeating the same diagnostic pattern — diagnosing 'missing import' on every iteration and regenerating a patch that failed in the same way each time. The escalation service detected this stagnation pattern and injected corrective instructions that forced a strategy pivot, often resulting in a successful repair on the subsequent iteration.
Fourth, the choice of Meta Llama 3.3 70B as the primary model was driven by both practical and technical considerations. Llama 3.3 is available through multiple free-tier inference providers (Groq, NVIDIA NIM, Cerebras), enabling the platform to be developed and evaluated without incurring API costs. Additionally, Llama 3.3's performance on PHP code generation tasks was competitive with proprietary models during preliminary testing, making it a suitable choice for a research platform.
4.9 Limitations
Several limitations of this study should be acknowledged. First, the evaluation dataset is limited to three categories of PHP/Laravel errors (missing model references, incorrect namespaces, and missing imports). While these represent the most common AI-generated code failures in the Laravel context, the platform's performance on more complex error types — such as logical errors in business logic, race conditions, or multi-file dependency chains — remains untested.
Second, the mutation testing gate, while providing a valuable quality signal, can produce false negatives in cases where the generated test suite does not cover the specific code path that was repaired. A test suite that achieves 85 percent mutation score may still miss a critical edge case. The 80 percent threshold was empirically selected but is not guaranteed to be optimal for all error categories.
Third, the MCP server remains a prototype and was not evaluated under real IDE usage conditions. The latency characteristics of polling-based repair status updates via MCP may not be suitable for interactive developer workflows, and further work on streaming MCP transport is needed.
Fourth, the evaluation was conducted using a single primary LLM (Llama 3.3 70B). The platform's architecture supports multiple providers, but comparative analysis across different LLMs was not performed in this study. Future work should evaluate the platform's performance with other models to establish the generality of the repair methodology.


CHAPTER FIVE
SUMMARY, RECOMMENDATION AND CONCLUSION
5.1 Summary of the Study
This project designed and implemented an AI-Enhanced Code Repair Platform focused on PHP/Laravel REST API applications, addressing the persistent gap between AI-generated code and functional, production-ready backend services. The platform was motivated by the observation that while large language models have dramatically accelerated backend code generation, the PHP/Laravel ecosystem's reliance on strict architectural conventions, environment-specific configurations, and runtime dependency management means that AI-generated code frequently fails during actual execution in ways that neither static analysis tools nor existing APR systems can reliably detect and correct.
The platform was built on four core components. A Docker sandbox environment pre-loaded with PHP 8.3, Laravel 12.x, Pest 3, and Laravel Boost provides an isolated, reproducible runtime for executing untrusted code safely. A FastAPI coordinator service implements the thirteen-step iterative agentic repair loop, managing container lifecycles, streaming progress events via Server-Sent Events, and persisting every repair attempt in a SQLite database for forensic analysis. A multi-provider AI integration layer routes repair prompts through Groq and NVIDIA NIM endpoints using Meta Llama 3.3 70B as the primary model at temperature 0.0 for reproducible results. A React web interface provides real-time repair visibility through a three-panel SSE display with CodeMirror-based code editing.
The iterative repair loop incorporates Laravel Boost as a context enrichment layer, querying the live database schema and framework documentation relevant to each error before constructing the AI prompt. A mutation testing gate requiring at least 80 percent mutation coverage provides a second validation layer, ensuring that repaired code is not merely error-free but behaviourally robust. The escalation service prevents stuck repair loops by detecting diagnostic stagnation and forcing strategy pivots. Additionally, a prototype MCP server was developed to explore the feasibility of IDE-based repair invocation.
The evaluation framework, driven by a structured batch manifest, tests the platform against representative error cases across three failure categories — missing model references, incorrect namespace declarations, and missing import statements — comparing the full system against ablation variants to examine the contributions of Boost context enrichment and the mutation gate.
5.2 Recommendations
Based on the implementation experience and the evaluation results, four directions are recommended for future development of the platform.
First, the MCP server prototype should be completed into a fully tested, production-grade integration. The current prototype demonstrates the feasibility of exposing the repair engine as an MCP tool for IDE clients such as Cursor and Claude Code, but it requires comprehensive integration testing, error recovery logic, and authentication hardening before it can be recommended for real developer workflows.
Second, AST-aware delta patching should replace the current XML patch mechanism. The current approach applies full file replacements or string substitutions, which risks overwriting surrounding code that was not involved in the error. An Abstract Syntax Tree-aware patching system would identify the specific method or expression requiring modification and apply a minimal, targeted change, reducing the risk of introducing new errors while correcting existing ones.
Third, the escalation service should evolve from heuristic rule-based detection to a machine-learned classifier. The forensic iterations table accumulated during evaluation contains rich data about which diagnostic patterns precede successful repairs and which predict continued failure. A lightweight classification model trained on this dataset could predict impending strategy failures before executing expensive mutation tests, reducing the average cost per successful repair.
Fourth, the sandbox architecture should be extended to support Python/FastAPI and TypeScript/NestJS targets in addition to PHP/Laravel. The docker_service module's interface is framework-agnostic; implementing equivalent sandbox images for these frameworks would establish the platform as a universal APR orchestration engine applicable to the full spectrum of modern REST API development.
5.3 Conclusion
The AI-Enhanced Code Repair Platform demonstrates that agentic AI, bounded by strict Docker execution, Boost context enrichment, and mutation-tested verification, can address the persistent gap between AI-generated PHP/Laravel code and functional, production-ready backend services. The platform moves beyond basic code generation to function as an autonomous repair partner — one that not only proposes a fix but executes it in a real Laravel environment, tests it against the live application state, and verifies that the generated test suite is robust enough to catch regressions.
The integration of Laravel Boost as a context provider represents a practical contribution of this project within the PHP/Laravel APR space. By equipping the LLM with the same schema and documentation context that a developer would consult when debugging, the platform reduces the occurrence of hallucinated Eloquent patterns, missing service registrations, and incorrect namespace declarations. The evaluation examines this improvement and provides a baseline for future research into framework-aware LLM prompting for APR.
The platform's modular architecture — with clearly separated service layers for Docker orchestration, AI routing, patch application, and escalation — establishes a foundation that can be extended to other frameworks and languages. The prototype MCP server further demonstrates the potential for seamless integration with the broader Laravel AI ecosystem. This project contributes a working system and a methodology for the intersection of AI code generation and real-world framework execution, taking a concrete step toward making verified, tested code the standard output of AI-assisted development.
